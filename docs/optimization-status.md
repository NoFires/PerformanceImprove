# 从实测到修复

有明确可实施的方向，但三项症状不能靠同一个“清理内存”按钮解决。当前使用已有 Mod 的运行记录定位本体路径；用户报告原版也卡，仍需把本体成本与 Mod 放大程度分开比较。

|---|---|---|---|
| 长时间对象累积 | 洗点时 Fabric 可达的 Stopped 控制器 4→18，切图后仍18 | 保存并在 Stop 完成后释放原订阅句柄 | 已合并到PerformanceImprove 0.2.0并替换旧版安装；未游戏 A/B |
| 升级同步卡顿 | 预览复制约9.28s，其中法术书约7.29s；进展刷新单次1.31s | 分解法术学习/复制子步骤，减少重复计算；为进展 UI 做正确失效的复用 | 已查到逐级学法术、逐条 AddKnown、线性查找和事件路径；尚未改写 |

## 第一版选择与范围

首先实现订阅清理，因为已有静态代码、运行中的直接保留链、游戏自带取消实现三方证据，并且可以限制到控制器自身拥有的一个句柄。说明见 `docs/lifecycle-fix.md`。

法术书优化不能直接跳过 AddKnown、去重所有条目或禁止学习事件。当前实现中，AddBaseLevel 会按规则学习法术，复制随后又逐条 AddKnown；AddKnown 涉及临时法术、特殊法术表、线性查找、事件以及原有的重复条目语义。修改前必须测这些子步骤并验证升级、撤销、神话合书与 Mod 回调，否则可能只把卡顿换成法术丢失或规则差异。

加载优化也不能声称可以直接省掉全部28秒或9秒：区域内容本身需要初始化，反射结果可能确实需要更新。缓存必须有正确失效条件及内存上限，减少等待要验证画面和峰值；本轮没有足够证据给出“可以快多少”的承诺。

本轮不建议在缺少对照的情况下全关 Mod、清除旧存档设置、定时强制 GC 或清空资源缓存。这些动作会改变环境、增加卡顿或破坏原数据，且没有解决已经找到的所有权问题。

## 后续对照的环境变化

制作试验补丁后的完整核验发现，已有 **16 个 Mod DLL 与初始清单不同**，包括 ToyBox、PerformanceFix、DarkCodex 等；目前 Info.json 可见 ToyBox 1.7.33、PerformanceFix 1.8.5 等版本。游戏 Managed 程序集的哈希未变。详情在 `analysis/mod-hash-drift-20261021.json`，没有覆盖原始 inventory.json，也未恢复、改写这些 Mod。

因此之前两次运行报告是旧组合的历史测量，不能把新组合加补丁的结果直接与其比较后宣称改进来自本补丁。下一轮需先在当前组合、关闭新修复时记录一轮，再启用新修复重复同一操作。现有 `verify_workspace.py` 对旧清单的严格完整核验会因这些差异失败；失败不表示新修复改写了游戏，也不能忽略为“全部通过”。核心 IL、32 项独立修复检查和安装包校验已经分别通过。
