# 已成交可堆叠卖出物品清理

PerformanceImprove 0.3.0，2026-10-21。按用户最后指示实现：**玩家卖出的东西如果会堆叠，直接处理这次玩家卖出的那批；保留独特/命名装备与任务道具，普通附魔装备也可以清理。**

## 如何区分来源

本机 VendorLogic.Deal 中，游戏先发出交易事件、计算卖价并发钱，随后对每批卖出物品执行 ItemsForSell.Transfer(item, StoreItems)。本功能只替换这里的卖出转移指令，买入转移指令、金钱处理、成交条件与交易事件均保留。

符合规则的这批物品在进入商人仓库、与商人原生货物合堆之前被移出并 Dispose。因此即使商人原有11件、玩家这次卖3件相同物品，也只处理玩家这3件，商人的11件不变。不按蓝图删除商人所有同类物品，不根据 SellTime 猜测历史混合堆的来源。

只放进卖出栏但没有成交、取消交易、买入失败或拒绝成交，不会触发清理。此前已在商人库存里的旧货不扫描。**清理即时发生，已处理物品无法回购；需要回购时，应在成交之前关闭本功能。** 被保护的物品仍正常进入商人库存。

## 物品保护

“能堆叠”不等于“普通”：本机 IsStackable 允许不少命名/独特装备堆叠，所以必须继续执行最初要求的保护。

- 实际物品必须在玩家此次卖出栏，已写入本次成交的 SellTime，并且当前 IsStackable=true、已鉴定、未装备、可移除、未被释放。
- IsNotable、钥匙、文书、自然武器、额外实体部件/事实、外观覆盖、未知 Mod 类型和无法确认的物品均保留。
- 装备检查独立名称、描述和风味文本的**本地化键或共享文本引用**，不靠中文名称关键词，也不靠当前语言包能否翻译。独立命名/描述的装备保留；普通+2、+5等自动按类型和附魔生成名字的装备可以处理。
- 使用本机参考蓝图生成的保守元数据清单：1190种原版物品，其中494种带有原始附魔。附魔本身不构成保留条件，但新增/临时附魔、能力或组件与记录不匹配时保留。
- 参考蓝图中被对话、任务、Etude或过场引用的候选物品另行保留；有些普通奖励也会因此保留。没有唯一可靠的“独特装备”布尔字段，不用颜色或价格替代保护。
- 参考清单不等于所有 Mod 组合的证明；未知或被改写的物品优先保留。运行中会再次检查，不单凭静态GUID删除。

规则生成脚本 `scripts/build-vendor-item-catalog.py`，元数据报告 `analysis/vendor-item-catalog.json`；只提取GUID、类型与附魔关联等技术元数据，不复制游戏描述文本。没有新增存档自定义实体部件或售出数量账本。

## 释放、记录与错误处理

首先写入并刷新 merchant- 日志的 discard_intent 行，再调用原 ItemsCollection.Remove，重新检查移出的同一物品仍独立、安全、数量不变，最后 Dispose。这样使用游戏自身的移除通知、事实和实体注销路径。不会去遍历商人库存或释放其他集合里的物品。

如果物品在移除回调中被移动或变成需要保留的物品，不 Dispose；仍未被接收的物品转入商人仓库。日志失败、达到2MiB上限或清理异常会暂停后续清理；原生转移的异常不会被捕获重试，避免重复转移。完整 Mod 回调的副作用不能靠这些边界保证全部可回退。

因为被清理的垃圾不加入商人库存，商人仓库对此批垃圾的“添加物品”通知不会发生；原本的成交事件仍发生。这是功能行为差异，需与已装 Mod 实际测试。

## 验证

新功能40项独立检查覆盖真实 Harmony 的卖出/买入区分、发钱顺序、商人原有同类物品不变、拒绝交易、保护物品、日志失败、回调移动/改名、错误恢复、版本IL形状与开关持久化；另外105项旧功能/整合检查继续运行。没有执行实际游戏交易、真实 ItemEntity 的 Unity 生命周期或验证节省多少内存。

更新前会备份全部存档。清理会随游戏下一次保存持久化；关闭功能只影响以后成交，不能把已清理物品重新生成。回退需要按备份记录恢复对应旧存档，不能把审计日志当作完整物品备份。
